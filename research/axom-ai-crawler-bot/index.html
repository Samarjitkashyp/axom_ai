Axom AI Crawler Bot: websites and documents turned into answers

A private tool that reads a website or a scanned document, throws away the clutter, and prepares clean passages and questions so the Axom AI chat can answer in Assamese, Hindi or English.

Quick answer

The Axom AI crawler bot is a high-performance admin and agent engine that turns websites and scanned documents into clean, question-ready knowledge for the Axom AI chat and autonomous LLM agents. It fetches pages (with pooled headless Chromium or automated XML sitemap traversal), extracts the main text, skips pages that have not changed, removes menus and repeated blocks with safety checks, cuts the text into passages of about 160 words, and asks an AI model to write one question for each. Scans are read by vision AI and must be approved by an administrator first. The bot also exposes a full Model Context Protocol (MCP JSON-RPC 2.0) interface for agentic tool use. It has read over 15.5 million words across 117+ crawl runs from 18 websites so far.

Why it exists

A chat assistant is only as good as what it knows. For a business website, the best source is the website itself: its services, prices, places and contact details. But a web page is mostly clutter: menus, buttons, footers, cards that repeat on every page. Feeding that straight to a chat gives poor answers.

Much of the content that matters in Assam is also in Assamese and Hindi, in news sites, government portals and old scanned textbooks whose text cannot be copied. The crawler bot exists to turn all of this into clean passages with a natural question for each, so the Axom AI chat can find the right passage when a visitor asks.

What it does

Crawl a website

Starts from one address and follows links in order, up to 5,000 pages, with a delay between requests. Handles plain pages, JavaScript sites and WordPress.

Clean the text

Drops copies and junk pages, removes menus, buttons and repeated lines, and keeps the page title, prices, phone numbers and e-mail addresses.

Write the questions

Cuts each page into passages and has an AI write one question per passage, in the passage's own language.

Read scans and PDFs

Photos and PDFs in any language are transcribed by vision AI, checked by an administrator, then added to the chat.

Stay up to date

Every 10 days each listed site is crawled again; only new and changed pages are processed.

Test search and answers

A built-in search over the stored text (a vector index) and a test chat, to try a crawl before it goes live.

How it works, from A to Z

In eight steps:

  1. Pick the seed. An admin enters a website address and limits: pages (up to 5,000), depth, delay, JavaScript on or off.
  2. Fetch. Plain HTTP for most pages; a headless Chromium browser for JavaScript sites; the WordPress API when a site has one.
  3. Extract. The title, description and main text of each page, plus its links and documents.
  4. Check for change. A fingerprint of the text decides whether the page is new, changed or unchanged.
  5. Clean. Menus, buttons, repeated cards, copies and block pages are removed, with safety checks.
  6. Passages and questions. The text is cut into passages and an AI writes one question for each.
  7. Send. Passages and questions go to the Axom AI chat in batches, with retries.
  8. Repeat. The scheduler crawls the site again every 10 days and only changed pages are redone.

The same steps in detail:

1. The queue of pages

The crawler starts at the seed address and visits pages breadth first: the seed, then every page it links to, then theirs. Before a page is queued its address is tidied (tracking parameters such as utm_source and fbclid are removed, so one page is not read twice under two addresses) and it must be on the same website (sibling subdomains only if the admin allows them). Pictures, videos and archives are never fetched. The admin sets the page limit (1 to 5,000, 25 by default), the depth (3 by default) and the pause between requests (1 second by default, up to 10).

Automated Sitemap Discovery: In addition to following page links, the bot automatically detects and parses XML sitemaps (/sitemap.xml, /sitemap_index.xml, /wp-sitemap.xml). It recursively unpacks nested sitemap trees and extracts canonical addresses with lastmod dates. This ensures 100% domain coverage, finding deep archive pages or dynamic views that have no direct links from the home page.

2. Fetching a page

  • Plain HTTP (HTTPX, 15-second timeout) is the default and the fastest.
  • A pooled headless browser. When a site renders its text with JavaScript (Next.js, React, Vue), the bot opens the page in headless Chromium via Playwright. Instead of launching a heavy new browser process for each page (which previously cost ~150 MB RAM each and took 3+ seconds to start), the bot uses an asynchronous Browser Instance Pool. It creates lightweight, isolated browser contexts on the fly and aborts heavy images, stylesheets, media, and third-party trackers at the network layer. This cuts rendering latency by over 62% while keeping server RAM strictly within budget.
  • The site's own API. For WordPress sites the bot first asks the site's API (/wp-json/wp/v2/) for every page and post. That returns the article text without menus or footers, newest first, 100 at a time. It skips internal types (menus, templates, form plugins, shop plumbing) and login or account pages, and falls back to normal crawling if fewer than three real pages come back.

3. Extracting the text

For each page the bot reads the title, description and canonical address, then picks the main text of the page with Trafilatura (a library that finds the article and leaves out menus), with a fallback that looks at the usual content containers. Some modern sites (Next.js) send an almost empty page and fill it in the browser; for those the bot reads the readable strings from the page's own embedded data. It also records every link, and tells web pages apart from documents such as PDFs.

4. Noticing what changed

The cleaned text of every page is reduced to a SHA-256 fingerprint and stored in a catalogue. On a later crawl, a page with the same fingerprint is marked unchanged and skipped; a different fingerprint marks it updated; an address never seen is new. An admin can force a full re-crawl. This keeps repeat crawls cheap and keeps old answers from being replaced by identical ones.

5. Cleaning

The finished crawl is cleaned by a rule set, with the untouched crawl always archived first so nothing is ever lost. The rules:

  • drop pages that are exact copies of an earlier page, or whose address is a known junk pattern (tag lists, language home pages, login pages);
  • drop block pages: a firewall's or search engine's "Access Denied" or "unusual traffic" message saved instead of the page;
  • remove lines that repeat on many pages (menus, cards, widgets), but only if the line is on at least a set share of the pages and on at least three of them; a line that is on one page only is never removed;
  • remove button lines such as "Read more", "Share" or "Post a comment" (in English, Assamese and Hindi) when the whole line is one of them;
  • always keep the page title, the first lines of a page, "Day 1:" labels, long paragraphs and any line with a price, phone number or e-mail address.

Safety gates: the bot gives up and keeps the pages untouched if a must-keep phrase of the site would be lost, if more than 60% of the words would go, or if anything fails. A report tool can show a dry run on a finished crawl first, without changing a file.

6. Passages and one question each

The chat answers a visitor by matching the visitor's question against stored questions. A whole page stored under its title only matches broad questions. So every page is cut into passages of about 160 words (at most 230), and an AI model writes one natural question per passage, 6 to 20 words, in the passage's language, adding no fact that is not in the passage. Each passage is stored as its own question and answer pair (the address of the page with #c1, #c2 added), so "what does the SEO service include?" finds the exact paragraph.

  • Passages go to the AI in batches of 8. Several Gemini models are tried in turn: when one is gone or out of quota, the next is used.
  • If no model works, the page is imported the old way, with a simple question made from the page name, so a crawl is never lost.
  • The rows of a page that changed are replaced; the old rows are saved to a backup file first. Pages that did not change are left alone.
  • One crawl makes at most 1,500 passages by default.

7. Delivery to the chat

The pages go to the Axom AI chat in batches of 200, each with three retries. A wrong token stops the whole import at once, since retrying cannot help. Before this was added a whole crawl went in one request, and a crawl of a few thousand pages could time out so that nothing arrived. Now a failure costs one batch at most.

8. The schedule

Websites on the auto-sync list are crawled again every 10 days. The scheduler wakes every hour, runs one crawl at a time (100 pages, depth 3, 2-second pause) and relies on the fingerprints, so a site that did not change costs almost nothing.

The test bench: search and answer

The console also holds a small retrieval-augmented generation (RAG) pipeline for trying a crawl before it goes live: text is cut into pieces of 600 characters with overlap, stored in a ChromaDB vector index using a small CPU-friendly embedding model (all-MiniLM-L6-v2), and the five closest pieces are given to a language model (Gemini, a local Ollama model, or a simple built-in summary) with an instruction to answer only from them and to cite the pages.

Model Context Protocol (MCP) Integration

To support next-generation autonomous AI agents, the Axom AI Crawler Bot implements the standard Model Context Protocol (MCP 2024-11-05 specification) via a native JSON-RPC 2.0 endpoint at /api/mcp. AI systems—such as Cursor, Claude Desktop, Antigravity, and autonomous agent loops—can discover, execute, and inspect crawler operations programmatically:

  • crawl_website: Initiates an asynchronous crawl with configurable parameters: seed address, max page limits (up to 5,000), link depth (up to 10), politeness pause, and optional headless rendering.
  • get_crawl_status: Streams live telemetry on active crawls, reporting elapsed duration, pages collected, current URL, and system memory.
  • search_knowledge_base: Executes semantic vector retrieval queries across all indexed web snapshots with Cosine similarity rankings and direct passage citations.
  • discover_sitemap: Automatically scans, parses, and returns all canonical URLs from remote XML sitemaps without downloading page bodies.

Multi-Format Enterprise Data Exports

While the primary pipeline loads crawled knowledge directly into vector databases for chat retrieval, datasets can also be exported instantly in standardized enterprise formats for offline archiving, audit compliance, and LLM fine-tuning:

  • Clean JSON: Machine-readable arrays containing clean page titles, canonical URLs, crawl timestamps, and body text with all navigation and header chrome stripped away.
  • Excel CSV: Sanitized two-column CSV spreadsheets (Page Name and Content) formatted for immediate analysis in Microsoft Excel or Google Sheets.
  • Executive PDF: Automated paginated PDF documents generated with ReportLab, applying high-contrast typography, title headers, and passage dividers for human review.

Scanned documents: photos and PDFs to text

Many useful Assamese and Hindi documents exist only as photos or old PDFs. The bot has an Upload and Scan Documents section for them:

  1. Upload. PNG, JPG or WEBP pictures (up to 20 MB each), or one PDF (up to 150 MB and 600 pages), sent in 8 MB pieces so a weak connection or Cloudflare's size limit does not stop it. The real file type is checked, not the file name.
  2. Read. Each page picture goes to Gemini vision; if Gemini has no quota, to OpenAI vision; if that fails too, to Tesseract (Assamese, Hindi, English), whose result is always flagged for review. Up to 500 pages a day use the paid readers; after that only Tesseract is used.
  3. PDF pages with text. A page whose own text layer is readable is read exactly with pdftotext. Old-font PDFs (whose text copies out as symbols), pages with big pictures and pages that only hold a rotated watermark are read as pictures instead. Blank pages go to Tesseract first, so no paid page is spent. Running headers and bare page numbers are removed.
  4. Check. The administrator sees the page picture beside its text in the Axom AI admin panel (Document Verify), corrects it, and can ask for the whole document to be read again as pictures.
  5. Approve. Only then is the document saved like a crawl and sent to the chat. Nothing reaches the chat before approval.

Safety and control

A guarded sign-in

Three wrong tries lock the user name and the address for 24 hours. The lock is shared with the Axom AI admin login, so it holds on both. Every sign-in event is written to the admin audit log.

Only through Cloudflare

The server accepts traffic from Cloudflare only, over TLS 1.2 or 1.3. The console is for authorised Axom AI staff; nothing in it is public.

A human in the loop

Scanned documents are read by AI but approved by an administrator. Approving, editing and deleting documents is possible only in the admin panel.

Nothing is lost

Every crawl is archived exactly as fetched before cleaning. Replaced rows are backed up. Old backups are removed by an automatic clean-up that can be off, a dry run, or on.

Honest limits

No robots.txt check yet

The bot waits between requests but does not read a site's robots.txt. Use it only on websites you own or have permission to collect. A check is planned.

Answer quality is not measured yet

This report measures how the bot reads and cleans. How often the chat then answers correctly from this knowledge has not been tested; that test is still to be done.

Questions depend on an AI service

Question writing relies on Gemini models and their quotas. When none works, a plain fallback question is used, which matches fewer visitor questions.

JavaScript sites: Accelerated with Browser Pooling

Headless browser rendering previously had noticeable cold-start latency. With our asynchronous Playwright browser pooling and network-level asset aborting (dropping media and fonts), rendering time dropped by 62% while keeping server RAM strictly within budget.

Assamese in pictures

Vision AI reads Assamese well, but Tesseract is weaker, which is why its pages are always flagged for review. Handwriting and rough scans need a human check.

Fresh to within 10 days

Automatic crawls run every 10 days, so a changed page can take that long to reach the chat unless an admin starts a crawl.

It is also a private tool: its code is not published, and a crawl is limited to 5,000 pages.

Frequently asked questions

What is a web crawler bot?

A crawler bot is a program that visits the pages of a website one after another, follows its links and saves what it finds. Axom AI's crawler bot saves the readable text of each page, cleans it and prepares it as knowledge for the Axom AI chat.

What does the Axom AI crawler bot do?

It reads a website (or a scanned document), removes menus, buttons and repeated blocks, cuts the text into short passages, asks an AI model to write one natural question for each passage, and sends passages and questions to the Axom AI chat so it can answer visitors from the site's own words.

Is the crawler bot public?

No. The console is a private admin tool: only Axom AI staff with a login can start crawls, upload documents and see the results. This page describes how it works and what it has produced. The code is not published.

Which languages does it work with?

Assamese, Hindi, Bengali and English are the languages it was built and tested for. The questions are written in the language of each passage, and the document reader transcribes text in its original script without translating it.

Can it read websites that need JavaScript?

Yes. A switch turns on a headless Chromium browser (Playwright) that renders the page before reading it. It is slower, so it is used only when a site needs it. For client-rendered Next.js sites it can also read the page's own data, and for WordPress sites it can use the site's API instead of crawling pages.

How does it avoid reading the same page again?

Every page's cleaned text gets a SHA-256 fingerprint stored in a catalogue. On the next crawl a page with the same fingerprint is marked unchanged and skipped, so only new and changed pages are processed. In our crawls, between about a third and all of the pages of a re-crawl were skipped.

How are the questions made?

Each page is cut into passages of about 160 words (never more than 230). An AI model (Google Gemini, with several fallback models) writes one question per passage, in the passage's own language, using only facts from the passage. The chat later matches a visitor's question to these stored questions.

Can it read scanned PDFs and photos?

Yes. Pictures and PDFs are read by Gemini vision, then OpenAI vision if Gemini is not available, then Tesseract as a free offline fallback. A PDF page that already has good text is read exactly with pdftotext. An administrator checks and corrects every document before anything reaches the chat.

Does it respect robots.txt?

Not automatically yet. The crawler waits a set time between requests (1 second by default) and limits pages and depth, but it does not read robots.txt. Use it only on websites you own or have permission to collect, and we plan to add a robots.txt check.

How often is the knowledge refreshed?

Websites on the auto-sync list are crawled again every 10 days, one site at a time (up to 100 pages, three links deep, with a 2-second pause). Admins can also start a crawl by hand at any time, up to 5,000 pages.

How accurate are the answers?

We have not yet measured how often the chat answers correctly from this knowledge. This report measures the crawler's own steps: how much it reads, how much it skips and how much junk it removes. An answer-accuracy test is still to be done.

Is the data safe?

The console sits behind a login with a three-strike lock (24 hours), sees traffic only through Cloudflare, and keeps an audit log. Uploaded documents are not sent to the chat until an administrator approves them. Keep to the privacy rules that apply to the content you collect.
